# `fs.readFile()` vs `fs.readFileSync()` vs `fs.createReadStream()`

## Quick Summary

| | `readFileSync()` | `readFile()` | `createReadStream()` |
|---|---|---|---|
| Execution | Synchronous | Asynchronous | Asynchronous |
| Blocks Event Loop | ✅ Yes | ❌ No | ❌ No |
| Loads entire file in memory | ✅ Yes | ✅ Yes | ❌ No — chunks |
| Best for | Small files, startup/scripts | Small-medium files | Large files |

---

## `fs.readFileSync()` — Synchronous

Reads the entire file **synchronously** — blocks the Event Loop until complete.

```javascript
import fs from 'fs';

const data = fs.readFileSync('config.json', 'utf8');
console.log(data); // file content available immediately on next line
```

**Pros:**
- Simple — no callbacks or Promises
- Result available immediately on the next line

**Cons:**
- **Blocks the Event Loop** — no other requests can be handled while reading
- Loads entire file into memory — bad for large files

**When to use:**
- Reading config files at **app startup** — before server starts accepting requests
- One-off scripts that run outside a web server context
- Never inside a route handler or middleware

---

## `fs.readFile()` — Asynchronous, Loads All at Once

Reads the entire file **asynchronously** — does not block the Event Loop.

```javascript
import fs from 'fs/promises';

// Using promises (modern approach)
const data = await fs.readFile('data.txt', 'utf8');
console.log(data);
```

**Pros:**
- Non-blocking — Event Loop stays free
- Simple API — easier than streams

**Cons:**
- Loads **entire file into memory** — problematic for large files (e.g. 2GB file → 2GB RAM used)
- Not suitable for very large files

**When to use:**
- Small to medium sized files
- Inside route handlers where you need the full file content at once
- Reading JSON config, templates, or small data files during a request

---

## `fs.createReadStream()` — Asynchronous, Chunk by Chunk

Reads the file in **small chunks** (default 64KB each) — never loads the entire file into memory.

```javascript
import fs from 'fs';

const readStream = fs.createReadStream('hugefile.csv', { encoding: 'utf8' });

readStream.on('data', (chunk) => {
  console.log('Received chunk:', chunk.length, 'bytes');
});

readStream.on('end', () => {
  console.log('Finished reading');
});

readStream.on('error', (err) => {
  console.error('Error:', err.message);
});
```

Real world usage — serving a large file in an HTTP response:

```javascript
app.get('/download', (req, res) => {
  const stream = fs.createReadStream('largefile.zip');
  stream.pipe(res); // stream directly to response — memory stays low
});
```

**Pros:**
- Memory efficient — constant low memory regardless of file size
- Faster time to first byte — starts processing before entire file is read
- Can pipe into other streams (HTTP response, compression, file write etc.)

**Cons:**
- More complex API — events or pipe required
- Need to handle backpressure manually if not using `.pipe()`
- Not ideal when you need the entire file content at once before processing

**When to use:**
- Large files — logs, videos, CSVs, zip files
- File download endpoints — pipe directly to `res`
- Any file processing pipeline — read → transform → write

---

## Side by Side — Memory Usage

```
2GB file:

readFileSync()     → 2GB loaded into RAM  ❌
readFile()         → 2GB loaded into RAM  ❌
createReadStream() → ~64KB in RAM at any time ✅
```

---

## Decision Guide

```
Is this at app startup (config, env)?
        └──▶ readFileSync() — simple, blocking is fine before server starts

Is the file small-medium AND you need full content at once?
        └──▶ readFile() — simple async, no memory concerns

Is the file large OR are you streaming to HTTP response?
        └──▶ createReadStream() — memory efficient, pipe to destination
```
