## Schema — Improvements

Your schema is mostly right but missing a few important columns:

```sql
user_sessions
├── id              (session id — use UUID, not auto-increment integer)
├── user_id         (foreign key → users table)
├── ttl             (time to live in seconds)
├── created_at      (when session was created / logged in at)
├── expires_at      (created_at + ttl — store computed value for faster queries)
├── last_active_at  (for sliding expiry — update on every request)
├── device_info     (browser, OS, device type — store as JSON string)
├── ip_address      (useful for security — detect suspicious logins)
└── is_revoked      (boolean — for force logout without waiting for TTL to expire)
```

**Why `expires_at` instead of just `ttl`?**

```sql
-- ❌ Your approach — has to compute every time
WHERE created_at + (ttl || ' seconds')::interval > NOW()

-- ✅ Better — direct comparison, faster, indexable
WHERE expires_at > NOW() AND is_revoked = false
```

**Why `is_revoked`?**

TTL tells you when a session naturally expires. But what if a user logs out early, or you want to force-logout a session? You need a flag to immediately invalidate a session without waiting for TTL to expire.

```sql
-- Force logout a specific session immediately
UPDATE user_sessions SET is_revoked = true WHERE id = 'session_uuid';
```

## One Race Condition to Be Aware Of

Your current approach has a subtle race condition:

```
User A and User B both hit the login endpoint at the same time
Both read active_count = 3 (limit is 4)
Both see 3 + 1 = 4 ≤ 4 → both allowed
Result: 5 active sessions — limit bypassed ❌
```

Fix with a database transaction and row lock:

```sql
BEGIN TRANSACTION;

-- Lock this user's rows so no concurrent check can read stale count
SELECT COUNT(*) FROM user_sessions
WHERE user_id = ? AND expires_at > NOW() AND is_revoked = false
FOR UPDATE;  -- ← row lock

-- If count < limit, create new session
INSERT INTO user_sessions (...) VALUES (...);

COMMIT;
```

This is rare in practice for a consumer app but worth knowing for an interview.

Your understanding is **mostly correct** but there is one important technical correction about what exactly gets locked.

---

### The Correction — Row Lock, Not Table Lock

`FOR UPDATE` does **not** lock the entire `user_sessions` table. It only locks the **specific rows returned by that query** — in this case, the rows belonging to that specific `user_id`.

This means:  

- User A's login request locks **User A's session rows** only
- User B can still login simultaneously without waiting — their rows are different
- Only two **simultaneous login requests for the same user** would cause one to wait

```
Request 1 (User A, device 1) → locks User A's rows
Request 2 (User A, device 2) → waits for User A's rows to unlock ✅

Request 1 (User A) → locks User A's rows
Request 2 (User B) → locks User B's rows — no conflict, runs in parallel ✅
```

---

### Your Understanding of the Flow — Confirmed ✅

For two simultaneous login requests from the **same user**:

```

User has 3 active sessions, limit is 4
        │

        │     └── FOR UPDATE locks User's session rows
```

### What Happens Without the Lock — The Race Condition

```
Both requests arrive at the same time
User has 3 active sessions, limit is 4
        │
        ├── Request 1 reads COUNT = 3 → 3 + 1 = 4 ≤ 4 → allowed
        │

              (reads before Request 1 commits its INSERT)

```

The lock prevents Request 2 from reading a stale count.

### One More Clarification — What `FOR UPDATE` Actually Locks

```sql
SELECT COUNT(*) FROM user_sessions
WHERE user_id = ? AND expires_at > NOW() AND is_revoked = false
FOR UPDATE;
```

`FOR UPDATE` locks the **rows that match the WHERE clause** —  
User A's active session rows. Any other transaction trying to:  

- Read those same rows `FOR UPDATE`
- Update those rows
- Delete those rows

...will be **blocked and made to wait** until the first transaction commits or rolls back.

This is precisely why Request 2 waits — it tries to lock the same rows, sees they are already locked by Request 1, and waits.

---

### Updated Mental Model

```
FOR UPDATE — Row-level lock (not table lock)
        │
        ├── Locks only rows matching WHERE clause
        ├── Other users' rows unaffected — they run in parallel
        ├── Same user's concurrent requests → one waits for the other
        └── Lock released on COMMIT or ROLLBACK
```

Your overall understanding of the flow was correct — the only refinement is that it is a **row-level lock** scoped to that specific user's rows, not a full table lock. This is important because a table lock would serialize ALL login requests across ALL users — which would be a serious performance problem in production.

Great question. The name `FOR UPDATE` is confusing because the query itself is a `SELECT` — not an `UPDATE`. Let me explain why it's named that way.

---

### Why It's Called `FOR UPDATE`

The name means — **"I am selecting these rows FOR the purpose of UPDATing them"**.

It's a signal to the database:

> "I'm about to modify these rows — lock them now so nobody else can touch them until I'm done."

```sql
-- You're saying to the DB:
-- "Select these rows AND lock them because I intend to update them next"
SELECT COUNT(*) FROM user_sessions
WHERE user_id = ? AND expires_at > NOW() AND is_revoked = false
FOR UPDATE;

-- Then you follow up with an INSERT/UPDATE
INSERT INTO user_sessions (...) VALUES (...);

COMMIT; -- lock released here
```

Even though you're only doing a `SELECT COUNT(*)` here, the `FOR UPDATE` tells the DB that a write operation is coming — so lock these rows now.

---

### Is `FOR UPDATE` the Only Way to Do Row Locking?

No — SQL provides multiple locking modes depending on your use case:

| Lock | Syntax | Blocks | Use When |
|---|---|---|---|
| Exclusive lock | `FOR UPDATE` | Other reads FOR UPDATE, writes | You will modify the rows after selecting |
| Share lock | `FOR SHARE` | Other writes, not reads | You just want to read and prevent others from modifying |
| Skip locked rows | `FOR UPDATE SKIP LOCKED` | Nothing — skips locked rows | Job queues — pick next available row |
| No wait | `FOR UPDATE NOWAIT` | Nothing — fails immediately if locked | When you don't want to wait — fail fast |

---

### Your Specific Case — Is `FOR UPDATE` the Right Choice?

Yes — `FOR UPDATE` is correct here because after the SELECT COUNT you immediately INSERT a new session. You are selecting to check, then writing — exactly what `FOR UPDATE` is designed for.

```sql
BEGIN TRANSACTION;

-- Lock User A's active session rows
-- "I'm about to insert a new session — lock these rows so count stays accurate"
SELECT COUNT(*) FROM user_sessions
WHERE user_id = ? AND expires_at > NOW() AND is_revoked = false
FOR UPDATE;

-- Application checks count, then:
INSERT INTO user_sessions (...) VALUES (...);

COMMIT; -- releases lock
```

---

### Simple Rule of Thumb

```
Reading rows and will modify data next   → FOR UPDATE (exclusive lock)
Reading rows and just want stable read   → FOR SHARE (shared lock)
Building a job queue, skip busy rows     → FOR UPDATE SKIP LOCKED
Want to fail immediately if row locked   → FOR UPDATE NOWAIT
```

For your session limit use case — `FOR UPDATE` is the correct and standard choice.
