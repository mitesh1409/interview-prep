# File Download Endpoint for Large Files

## Why Not `readFile()` or `readFileSync()`?

```
2GB file:

readFileSync()     → 2GB loaded into RAM all at once ❌ (also blocks Event Loop)
readFile()         → 2GB loaded into RAM all at once ❌
createReadStream() → ~64KB in RAM at any time        ✅
```

`readFileSync()` and `readFile()` load the entire file into memory before
sending it — for large files this can exhaust available RAM and crash the server.

---

## Use `fs.createReadStream()` + `.pipe()`

Reads the file in small chunks (default **64KB** each) and pipes them directly
into the response stream — memory usage stays consistently low regardless of
file size.

`.pipe()` also handles **backpressure** automatically — it pauses reading if the
client is consuming data slower than the file is being read, preventing memory buildup.

```javascript
import fs from 'fs';
import path from 'path';

app.get('/download/:filename', (req, res, next) => {
  const filePath = path.join(process.cwd(), 'uploads', req.params.filename);

  // Check file exists before streaming
  if (!fs.existsSync(filePath)) {
    return next({ statusCode: 404, message: 'File not found' });
  }

  const stat = fs.statSync(filePath);

  // Set headers so browser knows it's a file download
  res.setHeader('Content-Type', 'application/octet-stream');
  res.setHeader('Content-Disposition', `attachment; filename="${req.params.filename}"`);
  res.setHeader('Content-Length', stat.size); // lets client show download progress

  const stream = fs.createReadStream(filePath);

  // Handle stream errors — e.g. file deleted mid-transfer
  stream.on('error', (err) => {
    next({ statusCode: 500, message: 'Error reading file' });
  });

  // Pipe chunks directly to HTTP response — memory stays low
  stream.pipe(res);
});
```

---

## What the Headers Do

| Header | Purpose |
|---|---|
| `Content-Type` | Tells browser this is a binary file download |
| `Content-Disposition` | Forces browser to download rather than display it |
| `Content-Length` | Lets browser show download progress bar |

---

## Memory Comparison

```
Server with 512MB RAM serving a 2GB file:

readFile()         → ❌ tries to allocate 2GB — server runs out of memory
createReadStream() → ✅ uses ~64KB at any time — file size irrelevant
```

---

## What and Why

**Response headers** — without `Content-Disposition` the browser may try to display the file instead of downloading it. `Content-Length` enables the progress bar on the client side.

**Error handling** — the stream can fail mid-transfer (file deleted, disk error). Without a stream error handler, Node.js throws an unhandled error and crashes.

**Backpressure note** — `.pipe()` handling backpressure automatically is an important detail worth documenting — it's one of the main reasons to use streams over manual chunking.

**`fs.existsSync` check** — always verify the file exists before creating a stream, otherwise Node.js throws an uncaught error.
