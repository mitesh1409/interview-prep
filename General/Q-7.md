# Session Vs JWT: The Differences You May Not Know!

## Session-based Authentication/Stateful Authentication

**Flow of the Session-based Authentication**  

#1 User goes to login/sign-in page.  

#2 User logs in by providing login credentials (username/email + password).  

#3 Server checks/validates login credentials.  
If they are invalid then it returns 401 Unauthorized response.  
If they are valid then server creates a new session.  

Session data can be stored in one of the following ways:  

- server memory (non-persistent storage)
- database (persistent storage)
- in-memory cache like Redis (persistent storage)

Session data includes key information like user ID, session expiration time and other metadata.  

Then server sends back success response with a session ID.  

Server can send session ID using one of the following ways:  

- cookie (for web applications where the client is browser)
- response body (where the client is a native application e.g., mobile application, server is REST APIs)
- response header (where the client is a native application e.g., mobile application, server is REST APIs)

#4 Upon successful login, Client receives session ID in the server response  
(cookie/response body/response header).  
Client then saves this session ID on its side (in the local storage or cookie).  

#5 For the subsequent client requests where user authentication is required,  
client sends session ID (via cookie/request body/request header) to the server,  
server gets session ID sent by client.  
Server then validates this session ID, if it is valid then gets session data for this session ID.  
In case session ID is invalid or no user found for the session data (user might get blocked/deleted in between)  
then it returns 401 Unauthorized response, redirects to login.  

This is also called "Stateful Authentication" as the server maintains authentication state/data.  
Server is responsible for creating and storing session data.  
It then uses session ID as a key to retrieve this data on future requests.  
Client only saves session ID.  

**Key Pointers**  

* Separate storage required for storing session information.
* Invalidation of session is easy. Since the session data is stored on the server, the server can simply delete or invalidate the session at any time.
* Scaling also involves the session store.
* It is also called "Stateful Authentication" as the server maintains authentication state/data.
* Sessions are short lived.
* Server is responsible for creating and storing session data.
* In case of distributed system where your application runs on multiple servers, all those servers need access to the same session data. This is typically achieved by using a centralized session store that all servers can access, like Redis or a distributed SQL database. While this works well, it does add some complexity and potential latency to each request, as the server needs to make a seperate trip to the session store.

## JWT-based Authentication/Stateless Authentication

**Flow of the JWT-based Authentication**  

#1 User goes to login/sign-in page.  

#2 User logs in by providing login credentials (username/email + password).  

#3 Server checks/validates login credentials.  
If they are invalid then it returns 401 Unauthorized response.  
If they are valid then server creates a new JWT token and signs it with a secret key.  
This signature ensures the integrity of the token, preventing tampering.  

JWT token includes key information like user ID, token expiration time and other metadata.  

Then server sends back success response with a JWT.  

Server can send JWT using one of the following ways:  

* cookie (for web applications)
* directly in the response body (for native apps)

#4 Upon successful login, Client receives JWT in the server response  
(cookie/response body/response header).  
Client then saves this JWT on its side (in the local storage or cookie).  

NOTE: Client can read JWT but cannot modify it without a valid secret key (only server has this secret key).  

#5 For the subsequent client requests where user authentication is required,  
client sends JWT (via cookie/request body/request header) to the server,  
server gets JWT sent by client.  
Server then validates this JWT using a secret key, if it is valid then gets data from this JWT,  
and uses this data for authentication and authorization.  
In case JWT is invalid or no user found for the data (user might get blocked/deleted in between)  
then it returns 401 Unauthorized response, redirects to login.  

This is also called "Stateless Authentication" as the server does not maintain any authentication state/data.  
Server is responsible for creating and verifying JWT.  
All necessary data is contained within the token itself, which is stored on the client.  
Client stores JWT on its side.  
All the subsequent requests which needs authentication uses this JWT.  

**Key Pointers**  

* No separate storage required on server side.
* Invalidation of a JWT is not easy.
* Scaling client and server is easy.
* It is also called "Stateless Authentication" as the server does not maintain authentication state/data.
* Tokens are long lived.
* A Token can be stolen to hijack user account.
* Server has limited control over this token.
* Server depends on 3rd party library to generate and validate tokens.
  Computation is required to generate and validate tokens.
* Generally used in systems where we have native clients with REST APIs in the backend.
* Used in Serverless Architecture.

## More about JWT

### Algorithms to sign and verify JWT

For signing JWT there are several algorithms available, most common are:  

* HMAC
* RSA
* ECDSA

**HMAC** is a symmetric signing method, which means the same secret key is used to sign and verify the token.  
This is simpler and more efficient, but it requires sharing the secret key with any service that needs to  
verify the token, which can be a security concern.  

* Symmetric signing method
* Issuer and validator uses the same secret key, they share the key
* Security concern - the secret key is shared between multiple parties

**RSA** and **ECDSA** are asymmetric signing methods.  
They use a private key to sign the token and a public key to verify it.  
This allows for a more secure architecture where the private key is kept secret  
and only used for signing the token,  
public key can be shared with any service who need to verify the token.  
This adds some complexity and computational overhead compared to **HMAC**.  

The choice of signing algorithm depends on your security requirements and system architecture.  

If you have a Monolithic application or trust all the services in your system then **HMAC** might be sufficient.  

But if you have Microservice architecture or need to share JWTs with untrusted 3rd party services,  
then **RSA** or **ECDSA** provide a more secure solution.  

### JWT Expiration

One challenge with JWT is handling token expiration.  

If a token is stolen, it can be used until it expires.  

To mitigate this, you can use refresh tokens in combination with short-lived access tokens.  

The access token is the actual JWT used for authentication on each request.  
It has a short expiration time, typically around 15 mins.  

The refresh token, on the other hand, has a much longer expiration time, perhaps several days or weeks.  

When the access token expires, instead of requiring the user to log in again,  
the client can send the refresh token to a special token endpoint on the server.  
The server checks if the refresh token is valid and has not been revoked.  
If everything checks out, the server issues a new access token.  
This process happens behind the scenes, without requiring interaction from the user.  

This approach strikes a balance between security and user experience.  
The short-lived access token limit the window of potential misuse if a token is stolen.  
While the long-lived refresh tokens allow users to remain authenticated  
for an extended period without needing to log in repeatedly.  

It is important to note that the refresh token is only sent when the access token has expired,  
not on every request.  
The access token is sent on every request that requires authentication.

## When to use what?

**When to use Session-based authentication?**  

Session-based authentication is a good fit when you need the ability to revoke sessions instantly.  
If a user reports her account as compromised, you can immediately invalidate her session on the server side.  
Sessions are good choice if you already have a centralized data store for other purposes.  
You can leverage existing infrastructure for session storage as well.  
However, it is important to keep in mind that using a centralized session store  
does add some latency to each request, as the server needs to fetch the session data  
from the session store.  
Finally, sessions keep sensitive data on the server side, which can be a security advantage.  

**When to use JWT-based authentication?**  

JWTs are great choice when you need a stateless architecture.  
Because JWTs store all the necessary data in the token itself,  
your server doesn't need to keep track of sessions in memory or  
in a database.  

This makes it much easier to scale your application horizontally across multiple servers.  

JWTs are also useful when you need to share authentication data with other services.  

For instance, in a microservice architecture, a JWT generated by the authentication service  
can be verified and trusted by other services without needing to contact the authentication service  
on each request.  

If you do choose JWTs, consider implementing refresh tokens to balance security and user experience.  

Refresh tokens allow you to use short-lived access tokens to limit the window of potential misuse,  
while still allowing users to remain authenticated for an extended period.
