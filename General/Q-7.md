# Session Vs JWT: The Differences You May Not Know!

## Session-based Authentication

**Flow of the Session-based Authentication**  

#1 User goes to login/sign-in page.  

#2 User logs in by providing login credentials (username/email + password).  

#3 Server checks/validates login credentials.  
If they are invalid then it returns 401 Unauthorized response.  
If they are valid then server creates a new session.  

Session data can be stored in one of the following ways:  
- server memory (non-persistent storage)
- database (persistent storage)
- in-memory cache like Redis (persistent storage)

Session data includes key information like user ID, session expiration time and other metadata.  

Then server sends back success response with a session ID.  
Server can send session ID using one of the following ways:  
- cookie (for web applications where the client is browser)
- response body (where the client is a native application e.g., mobile application, server is REST APIs)
- response header (where the client is a native application e.g., mobile application, server is REST APIs)

#4 Upon successful login, Client receives session ID in the server response  
(cookie/response body/response header).  
Client then saves this session ID on his side (in the local storage or cookie).  

#5 For the subsequent client requests where user authentication is required,  
client sends session ID (via cookie/request body/request header) to the server,  
server gets session ID sent by client.  
Server then validates this session ID, if ok gets session data.  
In case session ID is invalid or no user found for the session data (user might get blocked/deleted in between)  
then it returns 401 Unauthorized response, redirects to login.  

This is also called "Stateful Authentication" as the server maintains authentication state/data.  
Server is responsible for creating and storing session data.  
It then uses session ID as a key to retrieve this data on future requests.  
Client only saves session ID.  

**Key Pointers**

* Separate storage required for storing session information.
* Invalidation of session is easy. Since the session data is stored on the server, the server can simply delete or invalidate the session at any time.
* Scaling also involves the session store.
* It is also called "Stateful Authentication" as the server maintains authentication state/data.
* Server is responsible for creating and storing session data.
* In case of distributed system where your application runs on multiple servers, all those servers need access to the same session data. This is typically achieved by using a centralized session store that all servers can access, like Redis or a distributed SQL database. While this works well, it does add some complexity and potential latency to each request, as the server needs to make a seperate trip to the session store.

---

## JWT-based Authentication

* No separate storage required on server side
* Invalidation of a JWT is not easy
* Scaling client and server is easy
* It is also called "Stateless Authentication" as the server does not maintain authentication state/data
